# 体验评审与验证

## 独立结果与输入

把现有界面、设计方案或实现变更，转成有位置、证据、影响、优先级、修正办法和验证条件的体验问题清单；需要时组织可用性测试方案并分析真实结果。

需要本次目标、目标用户与任务、评审范围和可访问成果。先检查实际可见界面、可操作行为及相关产品约定；截图可用于视觉判断，流程、权限、响应速度和隐藏状态须有额外证据。可以只审一个页面或流程，无需全产品审计。

缺真实用户、数据或运行环境时，仍可进行相应的专家评审/静态检查，明确未验证部分。对仅凭品味得出的意见说明其性质，不将其升格为普遍可用性缺陷。

## 方法：先取证，再判断与修正

### 1. 确立基线与验收任务

确认用户想改善的结果、关键路径、已有设计约束和本次变更。区分产品事实、已观察行为、统计数据、用户反馈、专家判断和假设。选择能暴露问题的代表任务，并事先写出完成标准。

度量按问题选择：任务完成、耗时、错误、求助、返工和主观理解；明确任务、参与人、样本、环境和口径。没有可比基线或实际观察时，不编造提升百分比或用点击减少直接证明效率。

### 2. 分层检查

| 检查层 | 核对内容 |
| --- | --- |
| 任务与流程 | 入口、当前状态、下一步、主任务闭合、返回/撤销、关键异常和恢复成本 |
| 信息与文案 | 用户概念、分组/导航、主次关系、认知负担、标签、提示和具体错误说明 |
| 视觉与一致性 | 可读性、中文排版、比例/对齐、内容密度、主动作、组件/状态与既有设计语言 |
| 适配与输入 | 实际目标设备、窄屏/宽屏、长文本、缩放、触摸、键盘与悬停替代 |
| 实现质量 | 关键控件、加载/错误/权限、模拟/真实边界、反馈与性能、设计还原 |
| 无障碍 | 对比度、语义/名称、焦点、操作顺序、状态通知、目标大小和适用标准 |

以NN/g原则辅助识别问题，每项结论仍需指向具体证据和影响；不能用原则名或任意总分替代分析。

### 3. Web无障碍基线

Web默认目标为WCAG 2.2 AA，检查本次范围内适用的A/AA要求；原生平台按其规范分别核验，不把CSS像素阈值直接套成所有平台尺寸。

- 文本一般对比度至少4.5:1，大文本至少3:1；WCAG的大文本口径为至少18pt，或至少14pt且粗体，并按标准核对适用例外。必要的控件识别和图形信息核对非文本对比要求。
- 关键操作可用键盘完成，焦点顺序有意义、可见且不被作者内容完全遮挡，无键盘陷阱；弹层关闭后按任务恢复焦点。控件有适当名称、角色、状态和关联标签，重要状态变化能被辅助技术获取。
- 文本可放大至200%而不丢内容/功能；检查320 CSS px宽度等标准重排条件及二维内容等适用例外，表格可按其任务保留必要二维布局。
- 指针目标原则上能容纳24×24 CSS px，逐项核对标准中的间距、等效控件、行内、用户代理和必要性等例外；此为AA最低目标，不替代产品更舒适或原生平台的触摸尺寸要求。
- 状态与错误不只依赖颜色或感官线索；错误定位与修正、冗余输入、可访问认证、拖动替代等按实际功能检查。

另外检查减少动态效果偏好与避免无必要运动，记录为体验建议或其对应标准级别，不能把所有动效建议都声称为AA必需项。上表只是常用检查入口，部分项通过不等于整个产品符合WCAG；合规声明须按完整标准范围验证。

自动工具只能覆盖部分问题；结合人工键盘、放大/适配与必要的辅助技术检查。未执行的检查记录为未验证，不能以“无自动报错”宣布无障碍合格。

### 4. 形成可执行问题清单

每项写明：位置/复现情境、观察证据、影响谁完成什么任务、依据/性质、推荐修正、验证任务和优先级。优先级使用：

- P1：核心任务受阻、重要误操作或无可行恢复路径，需优先解决。
- P2：可继续但造成明显错误、理解困难或重复劳动，安排近期修正。
- P3：主要影响一致性、细节或局部舒适度，随合理批次处理。

优先级结合影响、频率和恢复成本解释，不制造精确分数。范围不足以判断频率时标为未知；同一根因合并，不把大量相似症状当作研究深度。每项改法保持产品事实和授权范围；重大视觉/流程取舍给出依据与替代。

### 5. 按需进行真实用户测试

根据要验证的问题设计中性、真实的任务情境和成功标准；选择能代表目标用户与环境的参与者，先小范围试跑任务说明，避免在题目里暗示按钮或路径。记录实际操作、错误、求助、完成情况和反馈。

定性研究用于发现原因，定量研究用于比较指标；参与人数取决于群体和研究目标。小样本发现不外推为全体比例，不把固定人数当作普遍充分标准。没有真实参与者时交付测试方案和专家走查，AI模拟用户明确标注为假设检验辅助。

分析时区分观察、解释和设计建议，检查替代原因；性能环境、数据差异与任务熟悉程度会影响耗时，比较需注明条件。真实研究或录制涉及外部参与者和材料时按任务授权执行，设计方案不产生自动联系或发布权限。

### 6. 修正、复核与交付

对已授权且可执行的问题集中修正，用相同任务确认问题已闭合并检查受影响邻近行为；新问题/新变更再触发相应验证。交付问题清单、已修/未修状态、证据与检查范围、用户研究是否发生及尚存假设。

只评审时到具体建议与验证办法收口，不扩大改动；只允许视觉修改时指出流程问题及其影响，不擅自改业务规则。范围变化后更新同一清单与验收条件，不重启无关评审。

## 示例与验证边界

以下为模拟示例。

- 正例：表单提交后清空了用户输入。记录复现步骤和截图、说明重复录入成本，建议保留输入并定位错误，验证任务为修改一项错误后成功提交且其余值保留。
- 反例：看到低饱和配色就判定“高级感不足，建议全部重设计”。缺少用户任务、品牌依据和影响证据；应先分清偏好建议与实际问题。
- 边界例：只有静态截图。可审层级、排版和显露信息，键盘、错误恢复、真实耗时等标为未验证；不能宣称测试完整流程。

首版方法未证明任何具体产品已经改善。结构检查、当前Agent情境走查、真实用户测试、独立会话验证分别记录；证据见搭档验证记录。评审清单与用户研究材料属于具体项目/任务，无需跨任务能力状态。
