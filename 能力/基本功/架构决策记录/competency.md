# 架构决策记录

## 独立结果与边界

把重要取舍处理成能回答“为什么这样做、付出了什么、何时需要重评”的记录，并在需要时形成开发交接。适用于技术选型、边界/接口/状态所有权变化、兼容策略、关键质量和运行取舍，以及查询历史理由。

日常变量命名、常规配置修改和小修复无需 ADR。记录不是架构选择本身，也不能替用户批准方案。用户仅讨论时在对话交付；明确要求保存或当前任务已授权相关文档时直接保存对应范围，不逐步再确认。

## 输入与不足处理

必需：需要决定的问题、背景/约束、当前建议或已作决定及其来源。按需读取现有 ADR、相关设计和取证结果。

缺少历史决定依据时，记录当前事实与理由未知；重建的理由须标为推测或本轮新建议。不能从代码实现推断用户已认可。没有实际可行替代时如实说明条件，不编造已评估选项。

## 方法

### 1. 判断是否值得记录

检查决定是否跨越重要边界、影响长期修改/运行/数据/兼容成本，或未来容易被反复争论。若只是实施细节，在相关设计或任务说明中记录即可，不为凑数建立 ADR。

### 2. 核对既有记录与决定状态

查当前工程的记录位置和编号习惯，优先沿用唯一入口。读取相关现行、已替代记录；没有历史资料就保留未知。新记录默认 proposed，只有用户或可核实既有决策来源明确采用时才记 accepted。

proposed、accepted、rejected、deprecated、superseded 是项目决策记录的内容状态，不是 KSF 对象的 draft/active/archived；两者不混用。

### 3. 写清选择及代价

按 [ADR 模板](templates/adr.md) 组织：问题与约束、来源、候选及取舍、当前选择/建议、正负后果、风险、验证与重评条件。不能只列优点；临时约束和未验证假设必须能被未来读者找到。

可逆决定可简短；影响数据和公开接口的决定补上兼容、迁移和恢复限制。性能、费用、产品能力只写有依据的结论。推荐、用户确认、实际实施和验证是不同事实，分别标明。

### 4. 保存与替代

用户授权保存且位置明确时，复核最新目录与编号，避免覆盖并发新增。沿用已有约定；无约定时默认放实际工程 `docs/adr/`，编号采用四位递增数字，并维护同目录 README 索引。未明确实际工程时不把项目决策写进能力目录或 KSF Core。

新决定替代已接受决定时新增记录，旧记录保留原理由，仅更新状态及新记录链接；新记录回链旧记录并说明变化。纠正明显笔误或事实错误时标注修订依据，不默默改写历史理由。详见 [维护参考](references/adr-guide.md)。

### 5. 交接与复核

需要实施交接时使用 [交接模板](templates/implementation-handoff.md)：目标、已确定边界/契约、实施切片、验收、迁移/回退、未决条件和已授权范围。接口不能一边标已决定、一边让实施者重新选架构。

读取交接的开发者应能继续实现；实现中若发现架构前提不成立，返回受影响决定重评，不用代码悄悄取代当前方案。未解决条件不阻止无关工作，但依赖它的实施应明确受限。

## 质量与修正

每项重要选择有可回溯背景，接受的代价不被隐藏；状态能回到决定依据。记录中的目标和性能主张没有冒充测量。正文、索引和替代链接一致，历史理由保留。

若记录只有“采用 X 因为流行”，返回补问题、约束与可行替代。若用户纠正约束，更新本轮建议；已采用决定发生实质变化时新增替代记录，不将旧认可延伸到新方案。

## 案例

以下为模拟案例，不是用户实际决定。

- 正例：因离线运行和单写者约束，建议继续文件存储。记录它的并发限制、为何暂不采用数据库、将来多写者需求出现时的重评条件；用户未采纳前状态为 proposed。
- 反例：代码使用 Redis，就补写“团队评估后因延迟最低而选 Redis”。代码只能证明当前使用，不能证明历史讨论和性能对比。
- 边界例：已有 accepted ADR，本轮只解释历史理由。读取并总结现有记录，不自动新增 ADR 或让用户再确认既有决定。

## 支持与验证状态

模板和 [固定来源](references/sources.md) 可离线使用。保存使用实际工程的文件工具和适用规则；本基本功不自动创建仓库、提交、推送或发送通知。来源更新和长期维护不自动触发。

结构检查与案例走查不证明决策结果已落地。实际保存、采用、实施和验证分别报告。
