# 边界与交付标准

本文件由架构设计与模式选择基本功持有，是设计和评审共用标准。按当前任务选用；不适用项注明原因即可，不强迫每个小任务填完。

| 编号 | 要求 | 可检查证据 |
| --- | --- | --- |
| S1 职责 | 单元有可解释的职责与状态所有者；边界对应实际变化和隔离需求 | 职责说明、调用方、状态读写位置 |
| S2 依赖 | 依赖方向有理由；选用分层/六边形后内层不依赖具体外设；装配位置明确 | import/调用/装配代码，允许与禁止的依赖 |
| S3 契约 | 接口说明输入输出、前置条件、错误与副作用；消费者不依赖无意暴露的内部细节 | 类型、CLI/HTTP/文件契约及契约检查 |
| S4 状态 | 明确一致性和原子性边界；并发、中断、重试与恢复不破坏关键业务不变量 | 状态迁移、事务边界、重复/故障场景 |
| S5 故障 | 明确主要失败的检测、传播/降级、恢复与观测；信任边界处校验和授权有位置 | 失败路径、日志/错误边界、权限检查 |
| S6 质量 | 性能、可靠性、成本主张有目标及依据；未知不写成事实 | 当前资料、测量环境/负载/口径或明确验证计划 |
| S7 验证 | 验证围绕行为和风险；规则、接口、适配器在合适边界验证 | 测试/检查和所证明主张的对应，覆盖局限 |
| S8 演进 | 变化范围、消费者兼容、迁移、切换与回退条件可说明 | 可交付切片、数据处理、触发条件和恢复动作 |

标准用于判断具体设计，不预设某个框架、数据库或编程范式必然更好。没有选用某架构时，不能用其目录形式判断违规。例如脚本直接读文件可能合理；只有规则需要独立复用/测试而 I/O 纠缠阻碍它时才提出隔离。

将每个不满足项关联到具体影响。未取得证据时输出待验证问题；不要把“没有看到测试”写成“没有测试”，也不要把没有端口接口直接写成缺陷。
