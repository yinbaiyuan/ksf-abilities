# 架构模式选择参考

基于 ECC 与 wshobson 的方法做本地归纳。以下信号只帮助形成候选，不能自动推出结论；技术产品和版本能力须另行核实。

## 先问普通结构是否足够

同一进程、清晰模块、直接调用常是合理起点。优先在现有约定中隔离实际变化点。增加一种抽象就说明它将隔离哪种变化、保护哪个规则及增加什么成本。

| 候选 | 值得评估的信号 | 代价 / 何时不选 | 检验方式 |
| --- | --- | --- | --- |
| 分层 | 入口、业务与存储职责混杂，变化相互影响 | 空服务层和透传类增加跳转；小流程无需凑齐层数 | 从入口追踪职责，检查允许的依赖方向 |
| 模块化单体 | 单部署仍合适，但模块越过彼此内部数据和代码 | 边界治理仍要维护；目录拆分本身不能形成隔离 | 检查公开接口、私有状态和跨模块写入 |
| 六边形 / Ports & Adapters | 同一规则需多入口、换外设或离线测试；业务规则与 I/O 紧耦合 | 为每个函数加端口会过度抽象 | 用例使用假外设运行；真实适配器另做集成验证 |
| Clean Architecture | 业务规则被框架/ORM 驱动，内外层变化纠缠 | 映射和接口成本；不是所有 DTO 都需复制 | 检查领域/用例依赖和框架细节的位置 |
| DDD 限界上下文 | 不同业务范围同词异义，模型共享导致规则冲突 | 需真实领域理解；简单 CRUD 不强造复杂聚合 | 上下文语言、数据所有权、跨上下文映射 |
| 领域值对象 / 聚合 | 不变量被散落校验，多个对象需共同保持一致 | 大聚合会放大锁与加载；避免把整个系统当聚合 | 非法状态无法构造；更新保持业务不变量 |
| 微服务 | 已有清晰边界，独立发布/扩容/故障隔离有实际价值且团队能运维 | 网络、数据一致性、监控和部署成本；人数或用户总数不能单独决定 | 独立部署、故障隔离和数据所有权可验证 |
| 事件驱动 | 消费者需解耦或异步处理，业务能接受延迟与失败恢复 | 排错、顺序、重复、一致性更复杂；强同步结果不应硬改异步 | 重复、乱序、消费者失败与积压处理 |
| 事务 Outbox | 同一业务操作需写数据库并发布事件，双写中断会丢事件 | 需转发器、积压监控及消费者幂等，不保证端到端恰好一次 | 原子写入、中断恢复与重复投递测试 |
| CQRS | 写规则与读模型确有冲突或独立扩展需求 | 多模型与同步维护；单一慢查询不足以成立 | 读写一致性窗口、重建和收益测量 |
| Event Sourcing | 事件历史需作为事实源，重放/时态查询是核心需求 | 事件演进、重建、隐私删除和投影维护复杂；审计需求也可用普通审计日志 | 重放等价、版本迁移与敏感数据策略 |
| 防腐层 / Adapter | 外部或遗留模型正在污染内部语义 | 转换和错误映射需维护；无语义差异时可直接包装 | 外部变更不传播至领域，契约覆盖映射 |

## 六边形的最小落法

1. 选一个真实用例，写清输入、输出和不变量，不携带 HTTP 请求对象等传输细节。
2. 识别影响它的外部副作用，按业务所需能力定义最小端口；不要按某云厂商 SDK 原样复制。
3. 用例通过传入的依赖协调规则，适配器负责协议、序列化和存储转换。
4. 在明确装配位置绑定具体实现。接口归需要它的层所有，领域模型只持有真正的领域抽象。
5. 用假外设验证业务结果，以适配器契约/集成检查验证实际 I/O；分层不是只靠 mock 调用次数证明。

## 接口与一致性

先说明消费者和状态变化，再选择 HTTP、CLI、函数或消息。HTTP 需检查资源/动作、状态码、授权、分页和版本；CLI 需检查参数、退出码、stdout/stderr 和文件副作用；文件需说明格式、原子写入、编码和恢复。

有跨边界状态变化时，明确事务内外和失败后的可观测状态。重试必须限制次数/时间并区分可重试错误；有副作用时定义幂等或去重。补偿不能恢复所有外部动作，不能把 Saga 宣称为跨系统 ACID 事务。

## 渐进改造

从频繁变化且影响范围可控的一条流程开始。先记录行为，再用入口委托或外设包装建立边界，迁移和验证后才扩大。旧新路径的切换要能识别状态差异；涉及数据格式变化时单独设计兼容和恢复，不能默认切回旧代码即可。
